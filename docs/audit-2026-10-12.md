# Keeps audit — 12 October 2026

## Scope and method

Read-only application audit of the current checkout, split across three independent agents: frontend behavior; backend business logic and processing; security, cost controls and deployment configuration. The orchestrator checked types, smoke-tested the signed-out mobile UI and consolidated evidence. Application code and production data were not changed. Security review used the VibeSec skill.

P1 means fix before public launch; P2 means a material correctness or reliability defect. Reproductions below used isolated source-executing harnesses or the backend's in-memory fixtures, not production accounts. They are audit evidence, not committed regression tests.

## Findings

### 1. P1 — Crafted URLs bypass the SSRF guard through yt-dlp

**Location:** `backend/services/sources/social_video.py:65–67, 210–222`.

Social-video routing searches the entire URL for platform domain strings. An attacker-controlled public URL such as `https://public.example/tiktok.com` therefore enters the social-video downloader. yt-dlp's own page, redirect and embedded-media requests bypass the guarded HTTP client. Checking only the submitted URL does not constrain those subsequent destinations.

**Evidence:** With yt-dlp's transport fully mocked, the actual resolver and `_ytdlp_download` accepted a public HTML page containing a video at `http://127.0.0.1/private.mp4`, requested that loopback URL and returned the mocked media bytes. No real private-network request was made. Production internal-service reachability was not tested.

**Fix:** Match parsed hostnames exactly or by valid subdomain boundaries, and enforce address/redirect protections on every yt-dlp outbound request. Hostname routing alone does not secure downstream media requests.

### 2. P1 — Offline captures can replay into another account

**Location:** `frontend/src/lib/capture-queue.ts:7–17`; replay in `frontend/src/components/CaptureProvider.tsx:135–149`.

The offline queue uses browser-global storage and records URL/time without an owner. If user A queues a private URL, signs out and user B signs in, replay authenticates as B and saves A's URL into B's library.

**Evidence:** Actual transpiled queue code with mocked storage/authenticated ingestion reproduced A's URL being ingested as B.

**Fix:** Scope storage and replay to the originating Firebase UID, including in-flight replay across auth transitions. Do not transfer pending captures when accounts change.

### 3. P2 — Search responses arriving out of order leave a permanent loading state

**Location:** `frontend/src/routes/search.tsx:94–105`.

Effect cleanup cancels the debounce timer but not a request already running. If search B finishes before older search A, A overwrites both results and the settled query. The current query no longer equals the settled query, so the screen remains “Searching…” after all requests finish.

**Evidence:** Executed the actual effect with controlled promises; current query `travel` ended with settled query `pasta` and a loading state.

**Fix:** Ignore stale completions with a request generation or cancellation flag, or abort requests; apply the same guard to failures.

### 4. P2 — Failed POST PWA shares are not queued for retry

**Location:** `frontend/src/routes/share.tsx:86–109`.

POST shares carry a `shared` identifier and retrieve their URL from cached metadata. The failure handler instead reconstructs the URL only from legacy GET query parameters. On a retryable network/server failure it finds no URL, queues nothing and displays an error with a return-to-library action.

**Evidence:** Actual share effect supplied POST metadata and a rejected ingest produced an empty replay queue and an error.

**Fix:** Keep the resolved shared URL available to the failure handler and enqueue it under the correct account.

### 5. P2 — Regeneration completion can display the wrong note under the current URL

**Location:** `frontend/src/routes/notes.$noteId.tsx:94–114`.

Start regeneration for A, then navigate to B using next/previous. The route component is reused, and the watcher is cleaned up only on unmount. When A completes, its callback sets the displayed note to A under B's URL, including A's action-menu target.

**Evidence:** Actual callback with controlled job completion replaced displayed B with A. Installed router behavior and absence of `remountDeps` support parameter reuse.

**Fix:** Unsubscribe/reset on note or account changes and verify the active note identity before accepting asynchronous results.

### 6. P2 — Re-extraction recreates deleted notes

**Location:** `backend/routers/process.py:638–642, 669`.

Deleting a note while its re-extraction is processing or deferred does not cancel the job. The worker checks the target only to preserve its creation date; a missing target still reaches an unconditional `.set()`, restoring the deleted note.

**Evidence:** Worker executed with existing FakeDb fixtures and an absent re-extraction target completed successfully and recreated the document.

**Fix:** Require the target to exist at commit time using an atomic precondition or transaction. Coordinate deletion and outstanding jobs.

### 7. P2 — Metadata failure creates a fallback duplicate after a successful note write

**Location:** `backend/routers/process.py:669–677, 691–715`.

The structured note is saved before category/source registration and job completion. A subsequent metadata failure falls into the extraction-failure handler, which writes a second salvage document and points the completed job at that bookmark. Some Firestore failures do not enter the transient retry classification.

**Evidence:** Injecting failure in `add_user_category` after successful extraction left both the structured note and a fallback bookmark; the response selected the bookmark.

**Fix:** Atomically commit the note and successful job state, and isolate cosmetic metadata failures from extraction salvage.

### 8. P2 — A fallback document can defeat duplicate detection indefinitely

**Location:** `backend/routers/ingest.py:205–208`.

Duplicate lookup limits matching documents to one before excluding fallback notes. After a failed save followed by a successful retry, a fallback that sorts first hides the successful note. Later saves can spend another ingest allowance and AI call and create additional duplicates.

**Evidence:** Matching fallback and successful documents supplied to `_existing_note` returned `None` when fallback was first.

**Fix:** Find a non-fallback match before applying the limit, or maintain a canonical per-user URL lookup.

### 9. P2 — Optional enrichment can exhaust the worker lifetime before persistence

**Location:** `backend/services/enrich.py:34–42`; `backend/routers/process.py:629–645`.

Entertainment titles are enriched sequentially without a title bound or overall remaining-time budget. TMDB requests have individual timeouts, and embedding afterward has its own timeout. These operations do not respect the worker's remaining deadline and occur before the note is saved. Slow enrichment after expensive extraction can cross the hosting request limit, losing the result and causing repeat work or eventual failure.

**Evidence level:** Static control-flow and timeout inspection; not reproduced against live providers.

**Fix:** Reserve persistence time and apply a shared deadline across extraction, enrichment and embedding. Skip optional work when insufficient budget remains.

### 10. P2 — Deferred captures bypass per-user intake limits

**Location:** `backend/routers/ingest.py:59–64`.

Once the global quota is exhausted, the guard returns before incrementing the user's ingest count. An account below its daily limit can continue submitting unique URLs and accumulating deferred jobs. The drain does not enforce daily user limits or recheck the lifetime note cap. The burst limiter reduces the submission rate but does not bound accumulated work.

**Evidence level:** Static inspection of the transactional guard and deferred-drain path; not load-tested against production.

**Fix:** Charge accepted captures against per-user intake limits even when deferred, bound outstanding jobs per user, and enforce applicable limits when draining.

### 11. P2 — Deferred draining can exceed the global quota

**Location:** `backend/routers/process.py:378–399`.

The drain reads available quota once, dispatches work, then increments usage. Concurrent ordinary ingests can reserve those same slots. A failed dispatch also leaves a pending job without charging it; the stale sweep can later execute that job outside the quota accounting.

**Evidence level:** Static inspection of counter and dispatch ordering; no concurrent production test performed.

**Fix:** Atomically reserve quota and claim each job before dispatch, retaining the reservation through retries and redispatch.

## Suggested remediation order

1. Close yt-dlp SSRF and isolate offline queues by account.
2. Close deferred quota gaps, make note/job persistence atomic and preserve deletion semantics.
3. Fix frontend async races and POST share retry handling.
4. Correct duplicate lookup and enforce the complete worker deadline.

Add regression tests for the reproduced scenarios when fixing them. Passing the existing suite does not cover these failure modes.
